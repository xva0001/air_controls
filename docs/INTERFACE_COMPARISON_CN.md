# 桌面版與網頁版 — 介面比較報告

**專案：** AirCanvas — 手勢控制互動系統
**版本：** 1.0
**報告類型：** 結合專家啟發式評估與實測效能的比較性介面分析
**比較對象：** PySide6 桌面應用程式（`aircanvas/desktop`）與 FastAPI／HTML／CSS／JS 網頁應用程式（`aircanvas/web`）

---

## 摘要

AirCanvas 以兩個刻意設計成不同的交付平台，探索同一套手勢控制繪圖、導覽、滑鼠與物件追蹤系統。本報告就介面版面、互動設計、易用性、可及性、響應性、手勢回饋、系統整合、技術限制、效能與可維護性等面向比較這兩套介面。比較立基於單一核心架構：兩套介面皆實例化（instantiate）同一個 `InteractionSession`，因此行為上的差異可歸因於平台限制與互動調適，而非實作上的分歧。

桌面應用程式提供最寬廣的能力：原生作業系統的滑鼠與鍵盤導覽、可點擊穿透的透明覆蓋層、常駐的檢閱面板，以及即時的本地回饋。瀏覽器應用程式則提供最廣的觸及範圍與最簡便的散布方式：它可在任何現代瀏覽器上執行，能從三欄式工作室版面調適為行動裝置的抽屜面板，且除了本地 Python 服務之外無須安裝任何東西。瀏覽器在設計上無法在其他應用程式之上繪製、無法移動作業系統游標，也無法注入全域快速鍵。這些都被記錄為真實的安全邊界，而非缺陷。

一套 52 項測試的自動化測試套件、一次以真實手部影像進行的 MediaPipe 驗證、一組確定性的示範資料流，以及兩套介面的無頭（headless）算繪，共同為上述主張提供證據。本研究並未進行正式的使用者參與者研究；易用性一節為專家的啟發式審查，並明確說明其限制。

## 1. 方法與評估環境

### 1.1 產出物

| 產出物 | 建置版本 | 螢幕截圖 |
| --- | --- | --- |
| 桌面版，螢幕模式 | PySide6 6.12、Windows 11、1480×920 | `screenshots/desktop-screen.png` |
| 桌面版，鏡像模式 | 相同建置版本 | `screenshots/desktop-mirror.png` |
| 網頁版，螢幕模式 | FastAPI + Chromium 156、1480×920 | `screenshots/web-screen.png` |
| 網頁版，鏡像模式 | 相同建置版本 | `screenshots/web-mirror.png` |
| 網頁版，行動裝置版面 | Chromium 模擬，390×844 | `screenshots/web-mobile.png` |

建置機器配有實體網路攝影機，但程式代理沙箱會隱藏裝置。最終相機路徑已用全局 Python 3.15.1 在非沙箱環境驗證：MSMF、1280×720、約 4 秒處理 103 幀（31.5 FPS）、辨識 17.3 ms。MediaPipe 也在一張真實的 960×640 手部照片上完成驗證；螢幕截圖則使用明確標示為 `SIMULATED`（模擬）的資料流，該資料流會實際驅動真實的 `InteractionSession`、繪圖引擎、選取偵測器與 CSRT 追蹤器。瀏覽器的相機傳輸則以合成的 `MediaStream` 進行演練（權限、擷取、鏡像、JPEG 傳輸、狀態回復）。原生作業系統的滑鼠／導覽功能是以程式碼審閱與經單元測試的事件產生來演練，而非實際移動機器的游標。

### 1.2 方法

1. 依八項規格領域對兩套介面進行**功能檢視**。
2. 進行**程式碼層級比較**，以證明共用核心的重用情形，並辨識平台專屬的程式碼。
3. 以 Nielsen 的十大啟發式原則與 Shneiderman 的八項黃金法則進行**專家啟發式評估**。
4. 建立**功能對等矩陣**，標示完全支援／部分支援／無法提供三種狀態。
5. 於建置機器上進行**效能測量**。
6. **自動化驗證：** 52 項測試、Ruff 靜態檢查，以及瀏覽器執行期錯誤的收集。

**本評估的限制。** 本研究並未招募參與者，因此關於可學習性與滿意度的主張屬於分析性判斷，而非實證結果。相機被程式代理沙箱隱藏，但已用全局 Python 3.15.1 在非沙箱環境驗證。原生的點擊穿透／作業系統控制需要互動式的 Windows 工作階段與真實攝影機，才能完成完整驗收。

## 2. 介面版面

### 2.1 桌面版版面

桌面版是一個**原生、無邊框的工作室視窗**，採固定的三欄式構圖：

- **標題列：** 品牌、螢幕／鏡像分段切換器、相機狀態、已辨識手勢姿態、說明、視窗控制項。
- **左側工具列（228 px）：** 物件—動作（Object-Action）工具清單、筆刷調色盤、筆刷大小、智慧圖形、繪圖表面（畫布／桌面覆蓋層）、快速動作、穩定手勢提示。
- **中央舞台：** 紙張畫布或鏡像視訊，附情境標頭、浮動資訊片、相機子母畫面（PiP）或全幅畫面檢視、指標、追蹤框、選取軌跡與導覽 HUD。
- **右側檢閱面板（326 px）：** 手部骨架、手勢名稱／信心度、FPS／延遲／捏合指標、對應選單、調校滑桿、追蹤清單（鏡像模式）、相機／系統開關。
- **頁尾：** 狀態、快速鍵提示、FPS／延遲、視窗縮放握把。

版面為常駐式。它假設使用者擁有大型桌面視窗，並以「繪圖、手部回饋與設定能同時可見」為優先。另有一個獨立的透明全螢幕覆蓋層與一個浮動工具列，將繪圖表面延伸至應用程式視窗之外。

### 2.2 網頁版版面

網頁介面沿用桌面版的資訊架構，但採用**響應式 CSS 格線（CSS grid）**：

- **頂列：** 品牌、模式切換、相機／手勢資訊片、說明、連線狀態。在窄螢幕上，資訊片會收合，並出現抽屜按鈕。
- **三欄式工作區（>1120 px）：** 左側工具（232 px）、可伸縮的中央舞台、右側檢閱面板（326 px）。
- **≤1120 px：** 檢閱面板變成右側抽屜，由控制按鈕開啟。
- **≤820 px：** 左側工具列也變成抽屜；舞台佔滿視窗；頂列與頁尾壓縮。
- **左手操作：** 工具列移至右側、檢閱面板移至左側，在維持相同分組的同時，貼合使用者偏好的操作側。

網頁版面具流動性：中央舞台佔用剩餘寬度，而畫布的背景緩衝區會跟隨 CSS 尺寸 × 裝置像素比（device-pixel ratio）調整。行動裝置的螢幕截圖展示了「舞台優先」的調適方式；工具與控制抽屜仍可觸及。

### 2.3 比較

| 面向 | 桌面版 | 網頁版 |
| --- | --- | --- |
| 視窗模型 | 原生有框（自訂外觀）視窗，最小 1200×780 | 瀏覽器分頁，流動視窗 |
| 資訊密度 | 高且常駐；無抽屜 | 桌面為高密度；小螢幕使用抽屜 |
| 舞台主導性 | 中央欄位，兩側固定 | 中央欄位擴張；側面板變成覆蓋層 |
| 多螢幕 | 覆蓋層可使用整個主螢幕；原生視窗 | 舞台受限於瀏覽器視窗 |
| 行動裝置 | 不適用 | 完整響應式版面；支援觸控繪圖 |
| 視覺語彙 | 暖色深色表面、珊瑚色／薄荷色、寬鬆分組 | 相同的設計符號（tokens）、字體層級與分組 |
| 作業系統整合區域 | 原生控制項與桌面覆蓋層 | 瀏覽器外框 + 明確的原生限制說明 |

**解讀。** 桌面版版面最佳化的是*並行覺知*（parallel awareness）：工具、畫布、手勢與追蹤狀態可同時看見。網頁版版面最佳化的是*調適*：它保留相同的概念區域（工具、舞台、檢閱面板），但允許它們在空間受限時收合為抽屜。這是符合平台特性的差異，而非不一致：物件—動作的分組方式與概念順序維持不變。

## 3. 互動設計

### 3.1 共用的互動模型

兩套介面使用相同的五項物件與動作：

| 物件 | 動作 |
| --- | --- |
| 模式（螢幕／鏡像） | 切換工作區 |
| 工具（繪圖／導覽／滑鼠，或標註／追蹤） | 改變手勢的作用 |
| 筆刷／智慧圖形 | 改變繪圖輸出 |
| 手勢對應與調校 | 個人化辨識 |
| 已追蹤物件 | 選取、監控、移除 |

直接操作（direct-manipulation）的迴圈完全相同：手部位置移動一個可見的指標；穩定的手勢姿態啟動動作；視覺回饋立即出現；放開即結束動作；結果保持可逆。

### 3.2 桌面版互動設計

- **指標與點擊：** 舞台繪製環形游標／游標、按下狀態、點擊漣漪，並在啟用時顯示原生作業系統游標。手部骨架顯示於相機子母畫面或鏡像舞台中。
- **導覽：** 指標周圍會出現羅盤式的待發（arming）環；導覽提示先說明「按住以進入待發」，再說明「滑動」；浮動提示（toast）會指出動作名稱。
- **覆蓋層：** 在繪圖表面中選擇**桌面**，會開啟一個可點擊穿透的全螢幕畫布，外加一個獨立工具列。這是真正的*對桌面進行直接操作*，而非模擬效果。覆蓋層刻意設計為點擊穿透，因此退出方式是浮動工具列（而非畫布）。
- **原生整合：** 作業系統滑鼠與系統導覽都置於明確的確認對話框之後。系統絕不會在無提示的情況下接管游標。
- **鍵盤：** 模式／工具快速鍵、復原／重做、儲存與說明在應用程式內全域可用。使用者完全不使用手勢也能完成一次繪圖工作階段。

### 3.3 網頁版互動設計

- **瀏覽器相機：** 使用者需明確點擊**啟用相機**；瀏覽器的權限提示構成第二層同意。若權限取得失敗，啟動面板會給出確切原因，並提供模擬資料流或滑鼠繪圖的選項。
- **指標與點擊：** 虛擬的空氣指標與點擊漣漪在舞台內算繪。手勢點擊刻意設計為虛擬的；瀏覽器無法移動作業系統指標，也無法點擊其他應用程式。
- **繪圖：** 滑鼠／觸控的指標事件會以語意化的 `pointer` 階段送至共用的繪圖引擎；再將回傳的權威狀態予以算繪。相較於直接在本機 Canvas 上繪圖，這會多出一趟本地 WebSocket 往返，速度較慢，但可讓筆畫／圖形／復原的邏輯保留在 Python 端。
- **導覽：** 相同的待發／冷卻狀態會在舞台內算繪；瀏覽器層級的作業系統導覽無法提供，並已如此標示。
- **響應式控制項：** 在窄螢幕上，檢閱面板與工具變成抽屜；舞台仍是主要表面。畫布支援觸控繪圖，並使用相同的指標協定。
- **不隱藏原生能力：** 「系統」區段會明確說明哪些功能止步於瀏覽器邊界。

### 3.4 具實質影響的互動差異

| 互動面向 | 桌面版 | 網頁版 |
| --- | --- | --- |
| 相機擁有權 | Python／OpenCV 直接擷取 | 瀏覽器擷取後將 JPEG 送至本地 Python |
| 指標延遲 | 行程內約一個影格，30 Hz 介面輪詢 | 相機 + JPEG + WebSocket + Python + 狀態往返；端到端約 0.1–0.3 秒 |
| 原生點擊 | 可選的作業系統層級點擊／拖曳 | 僅虛擬點擊／漣漪 |
| 覆蓋層 | 真正可穿透的透明覆蓋層，覆蓋於其他應用程式之上 | 不可能；已於需求中記錄 |
| 繪圖輸入 | 手勢或直接在舞台上使用滑鼠 | 手勢、滑鼠或觸控（觸控使用相同的指標協定） |
| 瀏覽器相機選擇 | 不適用 | 取得權限後列舉裝置；否則退回預設裝置 |
| 多視窗 | 主舞台 + 覆蓋層 + 工具列 | 單一頁面；對話框為 `<dialog>` 模態 |

**解讀。** 桌面版更像原生創作工具：即時、多視窗、能跨越應用程式邊界。網頁版則像一個精緻、免安裝的*頁面內工作室*：在構造上更安全、更易攜帶，但刻意受到邊界限制。兩者都保留相同的手勢對應動作語意，因此學會其中一套的使用者，可將其概念模型移轉至另一套。

## 4. 易用性

### 4.1 首次執行與導引

- **桌面版：** 首次執行會顯示歡迎對話框，內含三張具體的手勢卡片、鍵盤提示、隱私權聲明，以及相機與模擬資料流的選擇。說明永遠只差一次點擊或一個 F1 鍵。
- **網頁版：** 一個 `<dialog>` 歡迎視窗說明相機權限，提供相機、模擬資料流與純滑鼠三種路徑，並保留「已歡迎」旗標。啟動面板仍可從相機狀態資訊片開啟。

兩套介面都使用平易的語言、顯示目前工具所需的手勢姿態，並避免為基本的滑鼠繪圖強制要求相機。這對於通用可用性，以及對於沒有網路攝影機的評審者而言，都很重要。

### 4.2 可學習性

- 使用中的工具狀態在視覺上十分顯眼（強調色條、標籤、快速鍵徽章）。
- 目前的手勢姿態、穩定姿態的信心度、按住時間與捏合比例皆為可見。
- 導覽會說明待發機制，而非期待使用者自行發現。
- 追蹤的狀態轉換（追蹤中、遮蔽、搜尋中、遺失、離開視野）皆有文字標示，而不僅以顏色區分。
- 智慧圖形校正會產生附帶信心度的成功提示，且結果仍可復原。
- 一個視覺化的「保持穩定」提示會說明動作未觸發的原因。

### 4.3 效率

桌面版在反覆性工作上較快：常駐工具、鍵盤快速鍵、直接的作業系統動作與多視窗。網頁版在*取得*上較快（輸入網址、無須安裝），且螢幕尺寸更有彈性。網頁版的相機往返與向量狀態傳輸會增加延遲，但不會增加概念上的工作量。

## 5. 可及性

### 5.1 桌面版

- 每個主要動作都有鍵盤快速鍵；自訂按鈕具備工具提示與可及性名稱（accessible names）。
- 大型點擊目標、高對比的暖色深色調色盤，以及可見的焦點環。
- 可調整的指標平滑度、靈敏度、按住時間與手勢姿態穩定度。
- 左手操作的版面排序。
- 模擬資料流與滑鼠繪圖是與相機同等地位（first-class）的替代方案。
- 原生視窗縮放；高 DPI 的捨入策略設為直通（pass-through）。
- 限制：自訂繪製的畫布與手部預覽並未以結構化的螢幕閱讀器內容呈現；手勢控制仍需要相機；沒有音訊提示；應用程式僅限桌面端。

### 5.2 網頁版

- 語意化的 HTML 地標（`header`、`main`、`aside`、`section`、`footer`）、跳至主要內容連結（skip link）、具標籤的表單控制項、附 `aria-checked` 的 `role="switch"` 切換開關、即時狀態區域與對話框語意。
- 可見的焦點樣式、鍵盤快速鍵、以 ESC 關閉抽屜／對話框，以及原生控制項；除模態對話框外，沒有焦點陷阱。
- 支援 `prefers-reduced-motion`；沒有任何必要資訊僅以顏色傳達（狀態文字均有附上）。
- 響應式版面與觸控支援；瀏覽器縮放。
- 限制：畫布是一個類影像的表面，無法提供筆畫幾何的螢幕閱讀器表述；相機權限由瀏覽器居中管理；部分快速鍵取決於頁面焦點；行動瀏覽器可能節流背景分頁。

### 5.3 比較

| 可及性面向 | 桌面版 | 網頁版 |
| --- | --- | --- |
| 鍵盤替代方案 | 強大；原生快速鍵 | 頁面內強大；瀏覽器可能攔截部分按鍵 |
| 螢幕閱讀器結構 | 具可及性名稱的自訂 Qt 元件，但畫布為視覺性 | 控制項具語意化 DOM 與 ARIA；畫布仍為視覺性 |
| 動作可及性 | 可調靈敏度、按住時間、滑鼠替代方案 | 相同的共用設定 + 滑鼠／觸控 |
| 視覺可及性 | 高對比、大型目標、信心度標籤 | 高對比、可縮放的 CSS、文字狀態 |
| 左手操作 | 完整面板重排 | 完整格線重排／抽屜側邊切換 |
| 無相機使用 | 示範 + 滑鼠 | 示範 + 滑鼠 |
| 行動裝置 | 無 | 有 |

**解讀。** 兩套介面在輸入替代方案、可調時間參數與無相機操作這幾個層次上，都是為*通用可用性*而設計。兩者都尚未完全解決自由手繪畫布的非視覺取用問題；這是領域層級的限制，已在未來工作一節中說明。

## 6. 響應性

### 6.1 版面響應性

- **桌面版：** 固定側欄與中央舞台。調整視窗大小會調適畫布與舞台；低於 1200×780 時內容會被裁切，因此強制套用最小尺寸。透明覆蓋層以主螢幕為目標，對多螢幕混合 DPI 的情況並不具響應性。
- **網頁版：** 斷點設於 1280、1120、820 與 560 px；控制項收合為抽屜；字級與間距壓縮；舞台維持主導地位。390×844 的螢幕截圖驗證了單欄行動裝置呈現。

### 6.2 即時響應性

- 桌面版管線以每秒 30 個已處理影格為目標，搭配 30 Hz 的介面輪詢；影格會被丟棄而非排入佇列。
- 網頁版約每 85 ms 送出一個相機影格（約 12 fps），並以顯示器更新率算繪；示範資料流的目標為 15 fps。
- 核心的媒體模型是向量狀態；筆畫不會被重新編碼為 JPEG，因此繪圖在瀏覽器縮放與高 DPI 顯示器下仍保持銳利。
- 網頁版的往返延遲明顯高於桌面版。本系統沒有本地的樂觀式筆畫預覽；這是刻意讓權威的 Python 狀態優先於重複的繪圖邏輯。這是在一致性與次影格延遲之間的有意識取捨。

### 6.3 回饋響應性

桌面版對原生指標／滑鼠回饋實際上即時；網頁版的回饋則需等待本地服務。兩者都以脈動／漣漪、手勢待發與追蹤狀態的動畫，傳達輸入已被接收。網頁版避免以每個影格轟炸介面（狀態更新會透過最新的快照合併處理）。

## 8. 系統整合

### 8.1 桌面版整合

- OpenCV 的相機列舉與擷取。
- Windows 原生游標移動、滑鼠按下／放開／右鍵、滾輪、`Alt+Left/Right`、Page Up／Page Down。
- 透過 `WindowTransparentForInput` 實現的置頂、**點擊穿透透明覆蓋層**。
- 檔案儲存對話框與 PNG 匯出。
- 以 JSON 形式保存的本地使用者設定。
- 應用程式層級的鍵盤快速鍵。

原生橋接（native bridge）是一個獨立模組（`native.py`），且僅由桌面版配接器呼叫。它預設為停用，並須經同意才啟用。

### 8.2 網頁版整合

- 透過 `getUserMedia` 使用瀏覽器相機；須明確授權；授權後可列舉裝置。
- 迴路（loopback）上的本地 FastAPI 服務；WebSocket；靜態資源供應。
- 僅限瀏覽器頁面內動作：繪圖、設定、匯出、虛擬指標。
- 沒有作業系統游標、沒有系統鍵盤注入、沒有覆蓋於其他應用程式之上的透明視窗、沒有未經使用者下載動作的檔案系統存取。
- 相機影格會被送至本地服務，但不會被儲存。瀏覽器仍是相機權限與分頁生命週期的擁有者。

## 9. 技術限制

### 9.1 桌面版

- 原生滑鼠／導覽為 Windows 專屬；透明覆蓋層的行為必須在目標 Windows 合成器與多螢幕組態上驗證。
- 相機權限由作業系統控制；應用程式無法繞過隱私設定。
- OpenCV 的擷取可能不支援所有特殊相機後端。
- 無邊框的自訂視窗需要 QSizeGrip 才能縮放；除作業系統層級的最大化外，沒有原生的視窗貼齊版面。
- 覆蓋層在設計上即為點擊穿透，因此其自帶的工具列才是可靠的退出方式。
- 即使 `num_hands=2`，每個影格仍只選取一隻手（最佳候選）；目前的互動模型使用慣用手。
- 在效能極低的裝置上，模型與追蹤器會受 CPU 效能限制。

### 9.2 網頁版

- `getUserMedia` 需要安全環境（localhost 或 HTTPS）與明確授權。
- 沒有透明覆蓋層、作業系統游標或全域鍵盤注入。
- 瀏覽器分頁的節流／背景暫停可能使相機影格停止。
- 裝置選擇需先取得權限，裝置標籤才會出現。
- 相機媒體會編碼為 JPEG 以便傳輸（品質／頻寬的取捨）。
- 瀏覽器僅是算繪端；若本地 Python 服務無法使用，辨識／繪圖狀態即無法使用。滑鼠繪圖同樣需要該服務，因為繪圖邏輯在設計上是共用的。
- 沒有跨工作階段的持久性個別使用者設定；伺服器會為每個 WebSocket 建立全新的工作階段。（瀏覽器其實可以保存設定；本建置刻意將工作階段視為短暫的。）
- 行動裝置的相機方向／長寬比可能有所不同；舞台採用內含縮放（contain-fit）與正規化座標以維持對齊。

### 9.3 共用／核心

- 規則式手勢可解釋，但表現力不如學習式的手勢分類器。
- CSRT／外觀追蹤並非語意化的物件辨識；外觀相似的物件可能造成混淆。
- 復原逾時（2.4 秒）與視野確認（約 6–10 個影格）是刻意的取捨。
- 圓形校正刻意採保守策略；它不會校正每一個迴圈，尤其在動態模糊下更是如此。
- 預設僅支援五個追蹤標記。
- 手部模型並非為本應用程式所訓練／微調；遮蔽與極端光照仍是限制。

## 10. 效能

### 10.1 實測行為

建置機器：Windows 11、完整 52 項測試與最終相機路徑均使用全局 Python 3.15.1、CPU 執行，無須獨立 GPU。

| 測量項目 | 結果 | 條件 |
| --- | --- | --- |
| MediaPipe 手部特徵點偵測器 | **平均 15.8 ms**、p95 為 17.2 ms、約 63 FPS | 960×640 真實手部照片，CPU |
| 示範工作階段（場景 + 合成手部 + 追蹤） | **25.6 FPS** | 5.86 秒內 150 個影格 |
| 桌面版介面輪詢 | 30 Hz | QTimer；處理落後時丟棄影格 |
| 網頁版示範資料流 | 目標 15 FPS，960×540 JPEG | 15 fps 排程；JPEG 品質 78 |
| 瀏覽器相機傳輸 | 目標約 12 FPS | 85 ms 間隔、0.64 JPEG、`bufferedAmount` 防護 |
| 網頁版畫布 | 顯示器更新率 | `requestAnimationFrame`、感知 DPR 的背景緩衝區 |
| 桌面版舞台狀態 | 30 Hz | QPainter 向量算繪 |

### 10.2 解讀

在測試機器上，CPU 推論的速度足以支援即時互動。網頁相機路徑中的主要延遲來源是傳輸 + JPEG 編碼／解碼 + Python 往返，而非手勢分類器。桌面版避開了影像傳輸，因此互動延遲最低。示範路徑（無相機）穩定且具確定性，這也是它被用於螢幕截圖的原因。

### 10.3 效能防護措施

- 以最新影格佇列／丟棄影格，取代無上限的緩衝。
- `bufferedAmount` 檢查可防止瀏覽器的傳送佇列不斷增長。
- 狀態快照具權威性並經合併處理；瀏覽器以最新狀態按顯示頻率算繪。
- 向量筆畫不會被重新編碼為影像；匯出是一次性算繪。
- MediaPipe 模型採延遲初始化（一次性約 1.2 秒的成本）。
- 追蹤復原的搜尋僅限於局部視窗，而非整個影格。

共用核心大幅降低了語意漂移。剩餘的重複部分是**呈現層**，這是恰當的：Qt 與 Canvas 需要不同的繪圖 API。`snapshot` 結構描述與事件語彙構成了核心與兩個算繪器之間的契約。自動化測試驗證核心與網頁傳輸；桌面版的冒煙測試驗證視窗與兩種示範模式。未來若要調整手勢門檻或追蹤策略，只需修改一處。

一項可維護性上的告誡：桌面版舞台與瀏覽器畫布都各自實作了相似的視覺基本元素（筆畫、追蹤框、骨架）。這正是共用*算繪規格*（顏色、尺寸、資訊片標籤）最能減少視覺漂移的主要領域。本專案目前以文件記錄共用的設計符號（tokens），並持續審查兩個算繪器；產生一份自動化的設計符號檔案，會是值得邁出的下一步。

## 12. 以不同方式套用的人機互動（HCI）原則

### 12.1 物件—動作介面

**兩者皆是：** 先選取工具（繪圖、導覽、滑鼠、標註、追蹤），再讓手勢作用於所選物件。左側工具列將工具分組；檢閱面板將對應／調校分組；舞台則將直接操作的產物分組。使用者不需要為不同工具記住隱藏的手勢。

**差異：** 桌面版擁有常駐的物件—動作表面；網頁版則在小螢幕上將物件清單收合為抽屜，因此在行動裝置上，操作序列變成*開啟工具 → 選取 → 關閉 → 操作*。這多了一步，但保留了模型。

### 12.2 直接操作

**兩者皆是：** 可見的指標跟隨手部；筆畫跟隨指尖；追蹤框跟隨物件；動作可逆。

**差異：** 桌面版可透過覆蓋層／原生橋接，直接操作作業系統桌面與視窗內容；網頁版的直接操作則受限於頁面畫布。網頁版以極為顯眼的虛擬游標與點擊漣漪作為補償。

### 12.3 Shneiderman 的八項黃金法則

| 法則 | 桌面版 | 網頁版 |
| --- | --- | --- |
| 1. 力求一致 | 與網頁版共用相同的手勢／顏色／標籤；遵循原生作業系統慣例 | 共用核心／語意；響應式版面改變位置但不改變標籤 |
| 2. 讓頻繁使用者得以使用捷徑 | 工具／模式按鍵、復原／重做、儲存、覆蓋層 | 相同的快速鍵，另加觸控；瀏覽器可能攔截部分按鍵 |
| 3. 提供具資訊性的回饋 | 即時骨架、信心度、導覽進度、原生點擊、追蹤狀態 | 相同語意；虛擬點擊與明確的瀏覽器／原生區分 |
| 4. 設計對話以產生完結感 | 圖形校正提示、追蹤鎖定／復原／離開視野等狀態 | 相同語彙；由伺服器狀態完成迴圈 |
| 5. 提供錯誤預防 | 手勢姿態穩定化、導覽待發／冷卻、作業系統同意、最小門檻 | 相同；另加瀏覽器權限閘門與更安全的「不涉及作業系統」策略 |
| 6. 允許易於回復 | 復原／重做、可逆的清除、移除標記 | 相同的快照歷程；清除可復原 |
| 7. 讓使用者保持掌控 | 明確的模式／工具、作業系統開關預設關閉、覆蓋層退出工具列 | 明確的相機／示範選擇、控制抽屜、不隱藏作業系統能力 |
| 8. 降低短期記憶負荷 | 常駐工具／檢閱面板、標籤旁的快速鍵、手部預覽 | 相同標籤、導引、舞台優先版面；行動裝置上抽屜可能需靠記憶 |

### 12.4 復原／重做與可逆性

兩套介面都提供復原／重做，並確認清除是可逆的。桌面版會顯示附有復原提示的浮動提示；網頁版亦同。桌面版的覆蓋層工具列包含復原與清除，因此使用者不需要回到主視窗。移除追蹤並不屬於繪圖歷程，但它是明確且立即的，且使用者可以重新選取。共用的歷程依模式（螢幕與鏡像）劃分範圍，可避免在其中一個表面復原時，意外移除另一個表面的成果。

### 12.5 通用可用性

- 無相機示範與滑鼠／觸控繪圖。
- 靈敏度、平滑度、按住時間、穩定度與對應設定。
- 左手操作版面與慣用手選擇。
- 鍵盤快速鍵、可及性標籤與焦點狀態。
- 高對比文字；狀態不僅以顏色區分。
- 瀏覽器原生縮放與響應式版面；桌面版感知 DPI。
- 網頁版增加了行動觸及；桌面版增加了原生能力。

### 12.6 格式塔（Gestalt）原則

| 原則 | 應用 |
| --- | --- |
| **接近性** | 工具清單、筆刷控制與快速動作構成左側一個「工作區」；對應／調校／追蹤／系統構成右側一個「檢閱面板」。 |
| **相似性** | 珊瑚色強調色一致標示作用中／主要項目；薄荷色一致標示追蹤／成功；琥珀色標示警示／待發；字體與 16 px 卡片圓角統一模組。 |
| **共同區域** | 卡片與面板邊框將相關控制項分組。舞台是一個圓角區域，容納所有直接操作的內容。在鏡像模式下，視訊矩形是畫面、標註、標記與手部骨架的共同區域。 |
| **閉合／連續** | 動作完成時，導覽進度環與選取軌跡在視覺上閉合；圖形校正提示則為繪圖動作畫下句點。 |
| **圖形／背景** | 深色介面表面框住米色紙張或即時視訊；光暈與括號覆蓋層將標註從繁雜的相機內容中區隔出來。 |

### 12.7 錯誤預防與復原

桌面版與網頁版共用相同的核心防護，但其復原表面有所不同：

- 桌面版可就作業系統控制呈現原生確認對話框，並能快速關閉原生功能。
- 網頁版使作業系統控制成為不可能，因此危險狀態較少；其風險在於相機／隱私，並以明確的權限與本地服務訊息加以處理。
- 兩者都提供附有「重試」與「模擬資料流」的明確失敗卡片，而非讓使用者走進死路。
- 兩者在辨識失敗時，都會確保*最後已提交*的繪圖狀態安全無虞；筆畫會被結束，且可以復原。

**依嚴重度排序的待改善問題**

1. **中度 — 行動裝置上的控制項探索：** 抽屜會藏住調校／追蹤功能；在窄螢幕上，頂列的控制按鈕僅有圖示而無文字標籤。若加上文字標籤或首次使用的箭頭指引，將有所幫助。
2. **中度 — 覆蓋層退出的可發現性：** 由於畫布為點擊穿透，只有浮動工具列能退出。該工具列是常駐且有標籤的，但全域快速鍵可改善復原能力。
3. **中度 — 網頁版延遲：** 由伺服器提供權威繪圖會延遲筆畫回饋。加入本地預覽層可改善感知延遲，但有重複邏輯的風險；任何實作都應僅止於預覽。
4. **低度 — 追蹤器遺失狀態：** 標記會保留以供檢視，但需要明確移除；可提供自動清理計時器作為選項。
5. **低度 — 螢幕閱讀器對畫布的取用：** 兩套介面都未將筆畫幾何呈現為結構化內容；未來若提供 SVG 匯出／描述面板，將有所幫助。
6. **低度 — 無相機的網頁繪圖需要本地服務：** 這是架構上的選擇（共用繪圖核心），且已由啟動面板／連線狀態清楚提示。

## 14. 討論

兩套介面體現了對同一個設計問題的不同答案：**能力應該駐留在何處？**

桌面版選擇了**能力與即時性**。它擁有相機、原生輸入橋接、多個視窗，以及一個點擊穿透的覆蓋層。它能參與自身視窗以外的工作流程。其代價是安裝、較大的螢幕需求、平台專屬程式碼，以及更大的安全表面（作業系統輸入）。該安全表面透過明確同意、預設停用與結束時釋放來管理。

網頁版選擇了**觸及範圍、安全性與調適性**。它可從一個網址取得、能在行動裝置上運作，且無法在無提示的情況下接管使用者的桌面。相機隱私由瀏覽器居中管理。其代價是喪失作業系統／覆蓋層能力、額外的傳輸延遲，以及對本地 Python 服務的依賴。這些代價都在介面、文件與功能矩陣中明確呈現，而非被隱藏。

從人機互動的角度來看，正是共用核心使這項比較得以自洽。若每套介面各自擁有辨識器，「桌面版與網頁版」的比較就會把平台差異與分歧的手勢行為混為一談。透過集中化辨識、門檻、繪圖與追蹤，本專案將**平台限制**隔離為有意義的變項。結果是一對介面，讓人感覺是同一產品的兩種表達，而非兩個互不相關的示範。

支持這項主張最有力的證據是結構性的：兩個配接器都呼叫同一個 `InteractionSession`，並算繪同一份快照。剩下的工作是呈現層的潤飾與非視覺的可及性，而非語意上的調和。

## 15. 結論

AirCanvas 展示了共用的 Python 手勢核心，如何在不重複電腦視覺或繪圖邏輯的前提下，同時支撐一個功能完整的原生創作工具與一個可攜式的瀏覽器工作室。

- **桌面應用程式**在延遲、系統整合、覆蓋層繪圖、常駐控制項與原生可及性上勝出。
- **網頁應用程式**在觸及範圍、免安裝取用、響應式／行動版面、構造上的安全性與示範便利性上勝出。
- **共用核心**在一致性、可維護性與可測試性上勝出。

因此，這場介面比較並非只有單一贏家的競賽。它示範的是符合平台特性的調適：桌面版延伸了使用者的作業系統工作區；網頁版則將相同的互動模型延伸到任何瀏覽器，同時尊重其安全模型。兩者對於展現此架構的優勢都是必要的。
